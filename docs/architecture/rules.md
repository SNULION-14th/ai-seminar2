# 아키텍처 규칙

## 기술 기반

- React + TypeScript + Vite를 사용한다.
- 기능이 성장해도 화면 계층, 도메인 로직, 인프라 접근을 섞지 않는다.
- 현재 템플릿 구조는 점진적으로 확장한다. 아직 필요하지 않은 전역 상태 라이브러리나 서버 계층을 미리 도입하지 않는다.

## 권장 소스 구조

기능이 생기면 아래 구조를 기준으로 확장한다.

```text
src/
  app/                 # 앱 진입, 전역 제공자, 라우팅, 전역 스타일
  features/
    <feature>/         # 화면 단위 기능: UI, 훅, 상태, 기능 전용 타입
  entities/
    book/              # Book 같은 핵심 도메인 모델과 표시 컴포넌트
    reading-record/    # ReadingRecord 같은 핵심 도메인 모델
  shared/
    ui/                # 여러 도메인에서 재사용하는 UI
    lib/               # 프레임워크 비종속 유틸리티
    api/               # HTTP 클라이언트와 공통 API 기반 코드
    types/             # 공통 타입
```

작은 규모에서는 파일을 과도하게 이동하지 않는다. 기능이 독립된 상태·UI·로직을 갖기 시작할 때 위 경계로 분리한다.

## 의존성 방향

`app → features → entities → shared` 방향만 허용한다.

- `shared`는 상위 계층을 import하지 않는다.
- 한 기능이 다른 기능의 내부 컴포넌트나 상태를 직접 import하지 않는다. 공통 도메인 모델 또는 명시적인 공개 API를 통한다.
- 페이지는 조합과 데이터 연결을 담당하고, 재사용 가능한 표시·입력 컴포넌트는 기능 또는 공유 계층에 둔다.

## 도메인 및 상태

- 핵심 모델은 최소한 `Book`, `ReadingRecord`, `ReadingStatus`, `RecordTag`를 독립 타입으로 표현한다.
- `ReadingRecord`는 책 식별자, 기록 본문, 작성 시각을 필수로 둔다. 감정/인상 태그와 독서 상태는 선택 또는 별도 관계로 다룬다.
- 서버에서 온 데이터, UI 폼 데이터, 화면 표시 데이터가 다른 의미를 가지면 타입을 분리하고 변환 지점을 한 곳에 둔다.
- 컴포넌트 내부 UI 상태는 가까운 곳에 둔다. 여러 화면이 실제로 공유해야 할 상태만 전역화한다.
- 비동기 데이터는 `loading`, `error`, `empty`, `success` 상태를 명시적으로 처리한다.

## UI와 접근성

- 기록 작성 화면에서는 입력과 저장 행동을 최우선에 둔다. 부가 설정은 접거나 선택 사항으로 제공한다.
- 버튼에는 동작을 나타내는 텍스트 또는 접근 가능한 이름을 제공한다. 아이콘만으로 의미를 전달하지 않는다.
- 폼 저장 실패 시 원인을 전달하고 사용자의 입력을 보존한다.
- 날짜와 시간은 사용자 로케일을 고려해 표시하되, 데이터 저장 형식은 일관되게 유지한다.

## 데이터·외부 연동

- 책 검색, ISBN 스캔, 인증, 저장소는 UI 컴포넌트에서 직접 호출하지 않는다. 기능별 서비스 또는 `shared/api` 경계를 통한다.
- 외부 응답은 경계에서 검증·정규화한 뒤 앱 도메인 타입으로 변환한다.
- 비공개 기록을 기본값으로 한다. 공유 기능은 사용자의 명시적인 행위가 있어야 한다.
- 개인 기록을 로그, 분석 도구, 공개 URL에 무단으로 포함하지 않는다.

## 테스트

- 도메인 변환·필터·정렬·리캡 계산처럼 순수한 규칙은 단위 테스트를 우선한다.
- 기록 작성과 저장처럼 핵심 흐름은 사용자 관점의 컴포넌트 또는 통합 테스트를 추가한다.
- 시각적 미세 조정만 하는 변경도 기본 빌드와 린트가 깨지지 않는지 확인한다.
